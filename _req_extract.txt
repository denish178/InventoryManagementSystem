 Project objective: Build a reliable inventory application to manage products, categories, suppliers, stock-in/stock-out movements, low-stock
alerts, and inventory reports. Every stock movement must be recorded, and stock updates must be protected by database transactions.
1. Project Overview
The Inventory Management System (IMS) will help a small business maintain accurate product and stock records. Users will manage
categories and suppliers, create and update products, record stock received or issued, view current stock, identify products at or below
their reorder level, and review inventory movement reports.
 Item
Decision
Application type
Web application with an ASP.NET Core Web API backend and a Angular frontend (recommended team baseline).
Backend
C#, ASP.NET Core Web API, Entity Framework Core, DTOs, dependency injection, validation, Swagger/OpenAPI.
Database
SQL Server with EF Core migrations and relational constraints.
Frontend
Angular (TypeScript) using standalone components, Angular Router, Angularive Forms, HttpClient, and a shared
service layer for API calls.
Version control
Git and GitHub; feature branches and pull requests.
Scope
Single business/location inventory in Version 1.0; no multi-warehouse, purchase-order workflow, or barcode scanner in
the initial release.
2. Goals and Success Criteria
  Maintain correct product, category, and supplier information.
  Ensure each SKU is unique and each product references valid category and supplier records.
  Prevent stock-out transactions from reducing inventory below zero.
  Record every stock-in and stock-out movement with quantity, type, date, and product.
  Display low-stock products when current quantity is less than or equal to the reorder level.
  Produce useful inventory and movement reports with date and product filters.
  Use a database transaction so a stock movement and its stock balance update either both succeed or both fail.

4. Functional Requirements
 ID / Feature
Requirement
FR-01 — Category Management
Create, list, view, update, and delete categories. Do not allow deletion when products are linked to the category; return
a clear validation message.
FR-02 — Supplier Management
Create, list, view, update, and delete suppliers. Validate required name and valid email format when email is supplied.
Do not silently delete supplier history or linked products.
FR-03 — Product Management
Create, list, view, and update products. Fields: name, SKU, category, supplier, unit price, current quantity, and reorder
level. SKU must be unique, price/quantity/reorder level cannot be negative, and foreign keys must be valid.
FR-04 — Product Search and
Filtering
Search by name or SKU; filter by category, supplier, and low-stock status. Support pagination/sorting if time permits.
FR-05 — Stock-In
Record received stock for a product. Quantity must be greater than zero. Increase current stock and create a
StockTransaction record atomically.
FR-06 — Stock-Out
Record stock issued/sold/removed. Quantity must be greater than zero and cannot exceed available stock. Decrease
current stock and create a StockTransaction record atomically.
FR-07 — Transaction History
Show product movement history with transaction type, quantity, and date, newest first. Allow filtering by product, type,
and date range.
FR-08 — Low-Stock Alerts
Show products where current quantity is less than or equal to ReorderLevel. Make the low-stock state visible in the
product list and dashboard.
FR-09 — Inventory Reports
Provide current-stock report, low-stock report, and stock movement report. Include totals and date/product filters where
relevant.
FR-10 — Validation and Errors
Return consistent HTTP status codes and useful error messages for duplicate SKU, invalid IDs, invalid quantity,
insufficient stock, and database failures.
FR-11 — Auditability
Every stock movement must be recorded. StockTransactions are append-only in Version 1.0; do not edit or delete
movement history through normal UI.
FR-12 — API Documentation
Expose Swagger/OpenAPI documentation for the API and document setup steps in the README.
FR-13 — Authentication
User login/logout and identity management
Use ASP.NET Core Identity for user accounts and password hashing. Provide login and logout/token flow, JWT bearer
validation, and secure handling of credentials. Do not store plaintext passwords.
FR-14 — Authorization
Role-based access control
Enforce Admin, Inventory Staff, and Viewer permissions on the API. Admin manages users/roles and all modules; Staff
can perform permitted inventory operations but cannot manage users/roles or delete master data; Viewer has read-only
access. Unauthorized requests must return 401 or 403 as appropriate.
5. Business Rules (Must-Have)
  SKU is required and unique, using a case-insensitive uniqueness policy if feasible. Enforce uniqueness in the database as well as in
 application validation.
 Stock quantities and transaction quantities are whole numbers greater than zero. If fractional units are needed, agree on decimal
 quantities before implementation.
 Stock-out quantity must never exceed available quantity. A failed stock-out must not create a transaction or change the stock balance.
  For every successful stock-in, increase Products.Quantity and insert one StockTransactions row in the same database transaction.
  For every successful stock-out, decrease Products.Quantity and insert one StockTransactions row in the same database transaction.
  StockTransactions.TransactionType should use a controlled set such as StockIn and StockOut; do not accept arbitrary strings.
  ReorderLevel cannot be negative. A product is low stock when Quantity <= ReorderLevel.
  Store transaction timestamps consistently (UTC in the API/database is recommended); display them in the user’s local time in the UI.
  Use decimal for UnitPrice, never float/double, to avoid monetary precision issues.
  Master data cannot be hard-deleted if doing so would break product or transaction history. Prefer a clear conflict response or
 soft-delete strategy.

Angular implementation standards
  Use Angular standalone components and Angular Router; organize the UI by feature rather than placing all screens in one component.
  Create typed interfaces/models for Category, Supplier, Product, and StockTransaction.
  Create injectable services such as CategoryService, SupplierService, ProductService, StockService, and ReportService using
 HttpClient.
 Use Angularive Forms for create/edit and stock movement forms; show field-level validation messages and disable submission while
 requests are in progress.
 Configure the API base URL through Angular environment configuration; do not hardcode localhost URLs throughout components.
  Use an HTTP interceptor for common error handling/loading or authentication headers if authentication is added.
  Keep stock balance changes exclusively on the backend stock-in/stock-out endpoints; the Angular UI must not directly edit a product's
 Quantity field.
Definition of done: a user can navigate through the Angular dashboard and pages, manage products, record stock-in/stock-out, view
updated quantities and transaction history, and open reports without manually editing the database.
8.1 Shared Responsibilities and Ownership Rules
  All members: pull latest changes daily, use feature branches, create pull requests, review at least one teammate’s change per
 milestone, and avoid committing secrets or local connection strings.
 All members: agree on route names, DTO field names, error format, and status codes before parallel implementation begins.
  Member 1 owns database schema and migration changes. Other members must coordinate schema changes with Member 1 before
 merging.
 Member 2 owns stock movement business logic and tests. Member 1 reviews database transaction/concurrency correctness.
  Member 3 owns frontend integration and reports UI, but report calculations must be returned by the API rather than duplicated
 inconsistently in the browser.
 Integration rule: do not wait until the end. Merge a minimal vertical slice (create product → stock-in → stock-out → view history) early.

10. Quality, Security & Technical Standards
  Use async/await for database and network I/O.
  Use DTOs and server-side validation; never trust frontend validation alone.
  Use EF Core migrations for schema changes and keep migrations committed.
  Keep secrets in User Secrets or environment variables; do not commit credentials.
  Use dependency injection and keep controller actions thin; place business rules in services.
  Use structured logging for unexpected errors; do not return stack traces to clients.
